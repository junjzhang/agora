1. Why — 我们在解决什么

现代工作流里，"并行" 的真实单位不是 shell session、不是 agent session、也不是 worktree——是 整个 project 上下文。

一个 project 的上下文不止是代码。它同时包含：

  • IDE（VS Code / Zed，可能绑一个 git worktree）
  • 多个 terminal（本地 shell、远程 SSH、Claude Code agent session）
  • 浏览器 tab（API 文档、wandb、Grafana、Figma）
  • 监控面板 / 论文 PDF / Obsidian note
  • 可能还有视频会议、AI chat 等杂项

现有工具各自只看到其中一维：

工具并行单位看不到
tmux / zellijshell sessionIDE、浏览器、远程
cmuxclaude code sessionterminal、IDE、辅助 app
conductorgit worktreesurface 多样性（只看代码面）
VS Code workspace pickerfolder活跃状态、agent 状态
niri workspace (原生)窗口容器project 语义、agent 状态

这个产品要补的空档：把 niri workspace 从 "窗口容器" 升级为 project context 容器，并绑定 agent 状态层。它是 cmux / conductor 的 上位抽象——它们是这层抽象的投影。

2. 定位 & 对比

一句话定位：

在 niri 上，把 project / issue / agent session 的编排统一成 keyboard-native 的操作，让切换、感知、创建 workspace 变成 effortless。

MAET 四维度——产品的价值面：

维度含义bash prototype 有？
Memory记住 project，快速再打开✅ MRU
Awareness每个 workspace 的 agent 在干什么（running/waiting/idle）❌
Environment打开 project 时该起哪些 surface（launch profile）⚠️ 硬编码
Todos / Intentproject 当前的工作意图（issue、tasks）❌

3. 核心概念模型

3.1 三层抽象

上层是 意图，下层是 物理：

Layer 1

Project

长期持有的工作上下文。粒度待定（repo / multi-repo / topic），见 Q1
Layer 2

Issue

project 内的一个具体工作单元。SoT 在外部 backend，见 §7
Layer 3

Surface

具体的一个窗口（terminal / editor / browser / pdf viewer）

这个三层比 cmux / conductor 都完整：

  • cmux 只有 Layer 2 的一个切片（claude session）
  • conductor 是 Layer 1+2 的合并（project ≈ worktree ≈ issue）
  • 我们是 1 / 2 / 3 全部建模，并让它们和 niri 的空间模型 1:1 对齐

3.2 Surface 的归属

Surface 不必属于某个 issue。归属有三种：

Project (workspace) │ ├─ Issue 1 │ └─ surfaces (0..N) ← 同 column 内 window │ ├─ Issue 2 │ └─ surfaces (0..N) │ └─ project-level surfaces (0..N) ← 同 workspace 但不属于任何 issue (project 根 ghostty/kitty、共享 IDE) (workspace 之外) └─ floating / external ← 谁也不属于（slack、邮件、随便看） 不在我们模型里

关键点：

  • Column 即 issue 的物理身份——同 column 的所有 window 都被默认判为这个 issue 的 surface。这是 niri 空间布局直接表达语义，没有独立的标注层
  • 没有 anchor / attached 之分。column 里所有 surface 平等。issue 的生命体征 = column 是否存在
  • Project-level surface 是 workspace 内不属于任何 issue 的 column——比如 project 根目录的常驻 terminal

技术注记 实测niri-ipc 的 Window event 直接给出 workspace_id 和 layout.pos_in_scrolling_layout: [col, row]。column 不需要独立 entity——"一个 column" = 同 workspace 同 col 的所有 window。manager 不存 column id，运行时按 (workspace_id, col) group 即可。

3.3 Project 数据结构

Project 是用户心智里的稳定 entity，不是 filesystem entity。name 是 id，path 只是 root 的属性。

Project {
  id: ProjectId,           // = name (string)，全局唯一
  name: String,            // user 显式命名
  roots: Vec<Root>,        // 所有 root 平等
  default_root: usize,     // 索引：默认 cwd / IDE 入口
  workspace_name: String,  // niri workspace name (默认 = name)
  pinned: bool,
  ts_created: u64,
  ts_last_active: u64,
  archived_at: Option<u64>,
  backends: Vec<BackendCfg>,
}

Root {
  path: String,
  host: Option<String>,    // None = local；只是 root 的属性
  label: Option<String>,   // "code" / "paper" / "data" / "train"
  launchers: Vec<Launcher>, // 自带 (snapshot)，无 profile 引用
}

Launcher {                 // host-aware：local/remote 自动派生命令
  VsCode | Zed
  Kitty { run: Option<String> }      // run=Some("claude") 起 kitty 后跑 claude
  Browser { url: String }
  Custom { argv: Vec<String> }
}

关键点：

  • name 是 id——project 稳定 key 是用户起的名字。path 改 / repo 移 / 远程换机器都不影响 project identity。special case → normal case
  • 所有 root 平等——没有 primary/attached 不对称。default_root 是 "首选项"，不是 "首要 root"
  • Launcher 是 host-aware——同一个 VsCode 在 local 和 remote 自动派生不同 argv（file:// vs vscode-remote://ssh-remote%2B...）
  • Root.launchers 是自给自足的 snapshot——不引用任何 profile，root 配方完全独立

3.4 Profile：snapshot 模板，非 live binding

Profile 不是 root 必须订阅的 "配置"，而是 创建 root 时可选的初始化模板——一次 copy，从此解耦。

# ~/.config/nwm/profiles.toml （v0.4 引入；MVP 内部硬编码）

[profiles.code]
launchers = [
    { kind = "vscode" },
    { kind = "kitty", run = "claude" },
]

[profiles.paper]
launchers = [{ kind = "zed" }, { kind = "kitty" }]

[profiles.data]
launchers = [{ kind = "kitty" }]

工作流：

  1. nwm root add memviz code ~/memviz-neo --from code → copy profile code 到 root.launchers
  2. nwm root edit memviz/code → 改 root 自己的 launchers，profile 不动
  3. nwm root snapshot memviz/code --as code-wandb → 把当前 root 配方存为新 profile
  4. Profile 不用删除——没有 root 引用它，留着也不占事

Trade-off：失去了 "改一处所有 root 一起更新" 的能力。但这是有意为之——产品哲学是 fluid，不让 user 维护一个 profile 库。改 profile 不影响存量 root。

┌─ workspace "memviz-neo" (= project) ──────────────────────────────────────┐ │ │ │ ┌─ column 0 ────┐ ┌─ column 1 (stacked) ─┐ ┌─ column 2 ────────────┐ │ │ │ issue MEM-42 │ │ issue MEM-43 │ │ project-level │ │ │ │ │ │ ┌───────────────────┐ │ │ (不属于任何 issue) │ │ │ │ [Claude Code] │ │ │ [Claude Code] │ │ │ │ │ │ │ │ │ ├───────────────────┤ │ │ [kitty @ project-root]│ │ │ │ │ │ │ [VS Code] │ │ │ │ │ │ │ │ │ ├───────────────────┤ │ │ │ │ │ │ │ │ │ [firefox wandb] │ │ │ │ │ │ │ │ │ └───────────────────┘ │ │ │ │ │ └───────────────┘ └───────────────────────┘ └───────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────────────────────┘ Mod+O → 换 project (workspace) Mod+H/L → 换 issue / project-level column ← niri scroll 的核心价值 Mod+Up/Dn → 换 surface (column 内 stack 切换)

4.1 数据来源 niri-ipc 实测

三层抽象到 niri event 字段的映射（niri 25.11，Request::EventStream 实测）：

抽象层niri 字段用途
Project Workspace { id, name: Option<String>, idx, output, is_active, is_focused } name = Some(...) 即 project anchor。改名走 WorkspacesChanged 全量快照，需 diff
Issue（column） 由 Window.layout.pos_in_scrolling_layout: [col, row] 推导 niri 不暴露 column entity，按 (workspace_id, col) group window 即得
Surface（window） Window { id, app_id, pid, title, workspace_id, focus_timestamp, ... } pid 是黄金钥匙：/proc/<pid>/cwd 反推 root → 自动认领到 project

关键信号：

  • focus_timestamp 每个 window 自带（独立 WindowFocusTimestampChanged event）——MRU 不用我们维护，直接 read
  • 没有 "workspace renamed" 专属 event——manager 须缓存上次 WorkspacesChanged 快照做 diff
  • 启动连接时 niri 主动推一次 full snapshot（WorkspacesChanged + WindowsChanged + ConfigLoaded）——daemon 直接拿来 init state，不需要额外 query

5. Issue 状态模型 decided

5.1 三维正交状态

Issue 的状态不是单一线性，而是 三个独立维度的组合。这是和 cmux / conductor / Linear 都不同的核心抽象。

维度取值SoT状态来源 / 推导方式
workspace
物理是否存在		 Dormant / Active manager (runtime) niri event stream 自动推导
agent
谁在干活		 NoAgent / Running / WaitingInput / WaitingPermission / Idle / Failed manager (runtime) agent hook 上报 + 进程 probe 兜底
backend
逻辑工作状态		 Backlog / InProgress / Done / Closed / None (scratch) 外部 (GH / Linear / Obsidian) backend pull + manager 主动 close 命令

三维 完全正交，可以任意组合。常见组合的语义：

workspaceagentbackend含义
DormantNoAgentBacklog立项了还没开始干
ActiveRunningInProgress正常工作中
ActiveWaitingInputInProgressagent 在等用户回复（中等紧急）
ActiveWaitingPermissionInProgressagent 在等授权（hard blocker，最紧急）
ActiveIdleInProgresscolumn 还开着但 agent 没在干（user 手工调）
DormantNoAgentInProgress临时 context switch 走了，回头要回来
ActiveNoAgentDone做完了，column 还没归档

5.2 Agent 子状态：Waiting 拆两档

"agent 在等" 这件事有两种本质不同的语义。混在一起会丢掉关键信息：

状态语义来源（Claude Code）UI 紧急度
WaitingInput agent 主动提问，等用户回复（"你想要 X 还是 Y"） Notification hook 🟡 中。可以 conversational 慢慢回
WaitingPermission agent 要执行 risky 操作，等授权（"要不要 rm 这个文件"） PreToolUse 拦截 (decision=ask) 🔴 高。hard blocker，打断流程
Running正常执行中process active🟢 无需关注
Idleagent 进程还在但没活动process active + N秒无 I/O⚪ 无需关注
Failedagent 进程异常退出exit code != 0🔴 失败提示
NoAgent没有 agent 在为这个 issue 工作—⚪ 无需关注

产品层面区别巨大：WaitingPermission 是 hard blocker——agent 完全不能动直到用户决定。DMS bar 用红色高亮 + 桌面 notification。WaitingInput 是 soft blocker——黄色提示就够。

5.3 状态推导规则

Workspace state 完全隐式推导：

ws=Active ⟺ issue 在 niri 里有 column（不论哪个 workspace、可见不可见）
ws=Dormant ⟺ issue 没有 column，但 manager 还持有它的 record

用户从不需要显式 pause / resume。manager 订阅 niri WindowOpened / WindowClosed 自动推导。

注意：ws state（物理）和 issue record 留存（逻辑）是两件事——

  • ws state 由 niri 状态自动推导
  • issue record 是否在 manager 表里活着，由 backend 状态 + 用户主动归档控制

它们正交。一个 issue 可以是 ws=Dormant + record=alive（暂存，picker 里能再开），或 ws=Dormant + record=archived（不在 picker 里露面）。

6. Issue 生命周期

典型轨迹（不强制顺序，issue 可在任意状态间往复）：

[1] 创建 ws=Dormant agent=NoAgent backend=Backlog │ user: nwm issue start MEM-42 / obsidian 里建了个 note ▼ [2] 激活 ws=Active agent=NoAgent backend=InProgress │ manager 在当前 workspace 开 column，但还没起 agent ▼ [3] agent 接管 ws=Active agent=Running backend=InProgress │ column 里起 claude code session，绑 issue ▼ [4] 等用户输入 ws=Active agent=WaitingInput backend=InProgress │ ↕ user 回复后 → 回 Running，往返若干次 │ [4'] 等用户授权 ws=Active agent=WaitingPermission backend=InProgress │ ↕ user 批准/拒绝后 → 回 Running ▼ [5] 闲置 ws=Active agent=Idle backend=InProgress │ user 离开但 column 还开着 ▼ [6] 完工 ws=Active agent=NoAgent backend=Done │ user/agent: nwm issue close │ → backend.close() → backend=Closed → record 标 archived ▼ [7] 归档 ws=Dormant agent=NoAgent backend=Closed │ manager 不强制关 column；user 自己关 window 后 ws→Dormant │ archived record 保留 TTL 期（默认 30 天）后才删除 ▼ [8] (可选) 删除 record 从 manager 移除（backend record 留着）

非典型轨迹示例：

  • context switch：[3] ws=Active → [关 column] → ws=Dormant；下次 picker 选中 → [激活] → 不同 agent session 接管
  • agent crash：[3] → agent=Failed → user 手动重启 → 回到 [3]
  • 跳过 backend：scratch issue 没有 backend，状态永远在 [2]-[5] 之间，[6]-[8] 只看 user 主动 close
  • auto-claim（PID 反推）3b 实测后可行：user 在 named workspace 里手动开 kitty 跑 claude → niri 推 WindowOpenedOrChanged{ pid, workspace_id } → daemon 查 /proc/<pid>/cwd 命中某 root.path → 直接进入 [3] agent=Running，不强求走 [1][2]。这是主流入口之一，不是异常路径

7. SoT 分层 & todo 抽象

核心原则：我们不是 todo 产品。我们是 workspace 产品。todo 的 source of truth 在外部，我们是 surface——绑定、展示、提供快捷动作。

7.1 SoT 归属表

数据SoT 在哪我们的角色
Workspace / project 注册表 (MRU)我们 (state.json)owner
Issue 内容 / 状态机外部（GH / Linear / Obsidian）read-only surface + close/status 动作
Issue ws / agent 实时状态manager (runtime)owner（来自推导）
Workspace ↔ Issue 绑定关系managerowner
Workspace ↔ Agent 绑定关系manager (runtime)owner

7.2 Todo 抽象层

不绑死具体 backend。定义一个内部 trait：

trait IssueBackend {
    fn list(&self, filter: Filter) -> Vec<Issue>;
    fn get(&self, id: IssueId) -> Option<Issue>;
    fn close(&self, id: IssueId) -> Result<()>;
    fn set_status(&self, id: IssueId, status: Status) -> Result<()>;
}

// 实现：
//   GithubBackend    (gh CLI)
//   LinearBackend    (GraphQL / OAuth)
//   ObsidianBackend  (vault markdown + frontmatter)

一个 project 可以配置 0..n 个 backend（大多是 1 个）。MVP 不做任何 backend；v0.3 先做 Obsidian 或 GH（看 Q2）。

7.3 集成边界（我们做什么 / 不做什么）

  • ✅ Bind：workspace / column 绑定一个 issue id
  • ✅ Read：显示 title、status、description、link 到原处
  • ✅ Inject：打开 issue 时把 description 注入 agent context
  • ✅ Close / 转状态：agent 完成后一键 close
  • ✅ Auto-archive：backend 进入 Closed → record 立刻标 archived（不再出现在默认 picker）。保留 TTL（默认 30 天）允许 unarchive；TTL 过后真正删除
  • ❌ Create / Edit issue：在 backend 原生 UI 做
  • ❌ Comment：同上
  • ❌ 强制关物理 column：archive 不动 niri，agent 可能还要清理输出，user 自己决定何时关

8. 核心动线

8.0 Project & Root 管理

nwm add ~/memviz-neo                          # 创建 project，name 默认 = basename
nwm add ~/memviz-neo --name memviz             # 显式命名
nwm add . --name memviz                        # cwd 简写

nwm root add memviz paper ~/memviz-paper       # 给 project 加 root
nwm root add memviz train gpu:/home/jovyan/... # 远程 root
nwm root add memviz data ~/data/memviz --from data  # 从 profile 初始化
nwm root edit memviz/code                      # 编辑 root.launchers
nwm root snapshot memviz/code --as code-wandb  # 把 root.launchers 存为新 profile

nwm rename memviz memviz-cv                    # 改 project name (atomic)
nwm root rm memviz/data                        # 移除 root

8.1 "我要回到某个 project"

Mod+O → 模糊匹配 "memviz" → Enter
  → manager 检查 workspace "memviz" 存在吗？
      是 → 切过去（focus-workspace）
      否 → 找一个空 workspace，set-workspace-name
  → 默认 launch roots[default_root].launchers（fluid + 最小打扰）

nwm open memviz --root paper      → 在同一 workspace 多开一个 column 装 paper root
nwm open memviz --all             → 一次性铺所有 root（每个 root 一个 column）

8.2 "我要在这个 project 里开一个新 issue"

project workspace 里按 Mod+Shift+N (或 nwm issue new)
  → manager 在当前 workspace 新开一个 column
  → 起 claude code terminal (cwd=project path, 绑 issue id)
  → 弹 picker 选 issue：
      · 从 backend 拉 "分配给我" 的 open issue 列表
      · 或选 "scratch" (无 backend issue)
  → 选中后 column 绑定 issue，agent 收到 issue description 作为 prompt

8.3 "这个 project 里的 agent 在等我吗？"

DMS bar / sidebar 常驻显示：
  🔴 memviz-neo   [MEM-42 · WaitingPermission] ← agent 等授权
  🟡 ml-paper     [#128  · WaitingInput]
  🟢 viz-core     [running]
  ⚪ scratch      [unlinked, idle]
点击某个 → 切到它的 workspace，column 已经聚焦到 waiting 的 issue

8.4 "issue 做完了"

在 issue column 里 Mod+Shift+X (或 nwm issue close)
  → manager 调 backend.close(issue_id)
  → record 立刻标 archived（picker 默认不见）
  → niri column 不动，user 自己决定何时关
  → TTL (30天) 内可以 unarchive；之后真删

8.5 "我要丢一个 project / 归档"

Mod+O picker → 选中 project → 右键 / context menu → archive
  → workspace 解绑，MRU 标 archived（默认不出现在 picker）

9. 已达成的共识 decided

  1. 并行的基本单位是 workspace（不是 agent session / 不是 shell）
  2. 我们是 surface，不做 issue 的 SoT
  3. 三层抽象：Project → Issue → Surface
  4. Niri 空间对应：workspace → column (可 stacked) → window
  5. Anchor 概念删除。column 即 issue 的物理身份，column 内 surface 平等
  6. Issue 状态是 三维正交：workspace × agent × backend
  7. Agent state 把 Waiting 拆成两档：WaitingInput (soft blocker) / WaitingPermission (hard blocker)
  8. Workspace state 完全隐式由 niri 推导，无显式 pause/resume
  9. Issue active 期间 最多 1 个 agent session（dormant 后可换不同 session 重新激活）
  10. Auto-archive on backend close：record 立刻标 archived，保留 TTL 期允许 unarchive
  11. Archive 不强制关物理 column，niri 状态由用户控制
  12. Todo backend 是一个 抽象层，不绑死 GH / Linear / Obsidian
  13. DMS plugin 走 "调 CLI 子进程" 方案，未来可选升级到 unix socket
  14. MVP 不触碰 issue / agent 层，只做 bash prototype 能力的 Rust 化
  15. Project name 是 id（显式命名，全局唯一）；path 是 root 的属性。重命名 path 不影响 project identity
  16. Project 内 所有 root 平等，default_root 索引指 "首选项" 而非 "首要 root"。primary/attached 不对称概念删除
  17. Multi-root 是一等公民（用户工作流 multi-root 场景频繁）。Root 包含 local 与 remote，host 只是 root 元数据，不参与 project 划分
  18. Launcher 是 host-aware，自动派生 local/remote 命令。MVP 内置 VsCode / Zed / Kitty / Browser / Custom
  19. Profile 是 snapshot 模板，非 live binding。root 配方自给自足，profile 仅在创建时被 copy；改 profile 不影响存量 root；profile 不需删除
  20. nwm open 默认只 launch default_root，--root <label> / --all 显式扩展

Q5 新 project 的冷启动 / launch profile decided

状态：decided 2026-04-27 · 收敛进 §3.4 profile 模型 + §8.0/8.1 动线

原讨论：硬编码 / repo 内 .nwm.toml / global 模板。基于用户哲学："profile 用完即弃、动态、不考虑删除" → 选 snapshot 模板模型：

final
  • Launcher 绑在 root（不绑 project / 不绑 issue），因为不同 root 类型差异大
  • Profile 是 snapshot 模板，非 live binding：root 创建时可 --from <profile> copy 一份；从此和 profile 解耦
  • nwm root edit 改的是 root 自带 launchers；nwm root snapshot --as 把 root 提升为新 profile
  • Profile 不需删除——没引用关系，留着无成本
  • Launcher host-aware：同一 VsCode 在 local/remote 自动派生命令
  • nwm open 默认只 launch default_root，--root/--all 显式扩
  • MVP 内置硬编码 system profiles (code/paper/data)，v0.4 引入 ~/.config/nwm/profiles.toml

11. Non-goals not doing

  • 不做 todo app。我们不存 todo 内容，更不管 deadline / reminder / notification。那是 Todoist / 滴答清单的事
  • 不做 issue 创建 / 评论。只做绑定、读取、关闭 / 状态转换
  • 不做 GUI 界面。所有 UI 由 DMS plugin（首选）/ vicinae / walker 提供，我们只提供 CLI + socket API
  • 不做 多 compositor 支持。只做 niri。hyprland 等别的 compositor 不在考虑范围，因为 column + scroll 模型是核心设计假设
  • 不做 远程/分布式同步。state 是 local file + systemd user daemon
  • 不做 团队协作。single-user 工具。团队协作交给 Linear / Github
  • 不做 显式 pause/resume issue。ws state 完全隐式由 niri 推导
  • 不做 强制关闭 column。archive 是逻辑动作，物理布局由 user 控制
